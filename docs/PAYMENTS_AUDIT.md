В поставляемой конфигурации нет разрешённых пакетов и нет активного контракта полей.

## Диагностический режим

Endpoint сохраняет только обезличенную структуру JSON/формы; значения произвольных полей
и исходный POST не сохраняются. Известные ключи сохраняют имена; остальные имена
хешируются, чтобы злоумышленник не мог записать email или секрет как имя поля.
Секрет проверяется до чтения тела. Ограничение тела — 64 КиБ, формы — 256 полей.
Дублирующиеся ключи отвергаются. `test=test` не создаёт заказ.
При неустановленном контракте создаётся `manual_review`, уведомление администраторам
с UUID и причиной. По диагностической структуре нельзя восстановить покупателя.

Для завершения аудита нужен приватно полученный обезличенный образец POST реального заказа:
сохранить имена полей и связи ID, заменить email, телефон, адрес и имя, удалить cookies
и API key. Сопоставить с серверным GET ЮKassa для того же payment ID; в публичный отчёт
поместить только названия путей и результат сравнения. Не использовать внешние публичные
request-bin сервисы с персональными данными или production-секретом.

Если payment ID или проверяемой связи заказа нет, остановить активацию.
Следующий шаг — согласовать с владельцем доступный способ получить надёжную связь;
изменение платёжного процесса и создание платежей на backend требуют отдельного решения.
Email, сумма, время и receipt-email эту связь не заменяют.

## Дополнение: конечный баланс администратора

По отдельному запросу владельца добавлена `011_admin_finite_balance` для Telegram ID
392172803 — именно ему миграция 005 назначала безлимит. При следующем запуске
`alembic upgrade head` отключается безлимит, баланс устанавливается ровно 100,
назначается указанный владельцем email. Разница баланса записывается в
`credit_transactions` как `adjustment`, старые операции не удаляются.
Администраторские права и доступ не меняются. Резервы сохраняются;
если они превышают 100 или email занят другим владельцем, вся миграция откатывается.
Повторное применение узнаёт корректировку по стабильному request_id и не сбрасывает
последующие траты. Downgrade не обращает финансовую операцию.
Нет подключения к рабочей базе Timeweb: применение там подтверждается только после
её миграции и проверки `/admin_user 392172803` и `/admin_email 392172803`.

После добавления корректировки администратора полный повторный прогон:
`pytest -q` на отдельном PostgreSQL 16 — **434 passed**, без пропусков,
одно предупреждение зависимости Starlette. `ruff check .` и
`ruff format --check .` также прошли.
