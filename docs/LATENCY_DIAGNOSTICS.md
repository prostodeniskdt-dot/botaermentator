# Диагностика паузы после принятия вопроса

Основание: после выпуска PR #3 пользователь сообщил о паузе 2–3 минуты между
уведомлением «Задачу получил» и ответом. Проверен `main` на `f663313`.
Настройки моделей и credentials Timeweb/Telegram недоступны. Первая предоставленная
выгрузка production-логов разобрана ниже; причина конкретной паузы пока не установлена.

## Подтверждено по коду и тестам

- Уведомление отправляется после проверки контекста и тематического фильтра.
  После него выполняются основной эксперт, сохранение и очередь доставки.
  Долгий классификатор влияет на время до уведомления, а не только после него.
- Клиент повторно перебирал все API-варианты при каждом вызове. В тестовом
  сценарии с поддержкой Responses API это четыре HTTP-запроса на каждый ответ:
  три отклонённых и один успешный. Такое поведение существовало и до PR #3.
- PR #3 направил сохраняемые ответы через один потребитель доставки. Он также
  ожидал редактирование кнопки и удаление уведомления перед следующим ответом.
  Зависание этих вспомогательных операций задерживало другие готовые ответы.
- `markdown_it`, используемый новым форматированием, отсутствовал в явных
  зависимостях. В чистом окружении это вызвало ошибку импорта при запуске тестов.
  Это отдельная проблема установки, не объяснение медленной успешной генерации.

## Изменения

- Успешный API-вариант используется первым для следующих вызовов того же агента.
  Профили с ограничением output и без него разделены; конкретный лимит и текст
  формируются заново. Предпочтение хранится в памяти процесса и истекает после
  десяти минут без успешного вызова. После перезапуска подбор выполняется заново.
  Если предпочитаемый API отклонён как несовместимый, перебор продолжается.
- Отправка с неоднозначным результатом по-прежнему не повторяется вслепую;
  ошибки доступа/квоты не обходятся переключением транспорта. Общий deadline
  и лимит HTTP-попыток сохранены.
- Удаление уведомления и редактирование кнопки ограничены пятью секундами каждое.
  Уведомление удаляется после всех частей ответа, перед редактированием кнопки.
  Незавершённое удаление остаётся для существующей фоновой очистки. Отправка
  текста и генерация не получают сокращённого таймаута.
- Добавлена явная зависимость `markdown-it-py`.

## Как различить причины после выпуска

Для одного запроса сопоставить `request_id`, `question_id` и `delivery_id`:

| Событие / stage | Что измеряет |
| --- | --- |
| `task_notice_send` | Отправку уведомления |
| `expert_generation` | Основной вызов Timeweb, с `question_id` и режимом |
| `agent_http` | Отдельную попытку и выбранный API |
| `delivery_queue_wait` | Возраст задания при взятии доставки; на повторах включает backoff |
| `telegram_send` | Отправку каждой части ответа |
| `answer_delivery` | Доставку целиком, включая БД и вспомогательные действия |
| `task_notice_delete` / `expansion_button` | Вспомогательные Telegram-запросы |

Небольшое ожидание доставки и большой `expert_generation` указывают на основной
вызов Timeweb. Большой `delivery_queue_wait` при уже завершённой генерации
указывает на доставку или её повторы. Проверять также `timeweb_http_error`,
`telegram_delivery_failed` и метрики БД. Не публиковать credentials и тексты
пользовательских запросов при передаче логов.

Предел чтения Timeweb 120 секунд и общий deadline 150 секунд близки к описанному
интервалу, но сами по себе не доказывают таймаут. Лимиты Quick/Deep, память,
основной экспертный промпт и правила пищевой безопасности в этой правке не меняются.
Новых миграций нет. Эффект на production и причину конкретного замедления нужно
измерить после установки версии в Timeweb.

## Разбор первой выгрузки логов

Файл `app-logs-225403-2026-10-23T21_16_12.562Z.txt` содержит ровно 10 000 строк.
Метки времени: 23 октября 2026, 21:09:21–21:16:22 UTC, то есть 24 октября
00:09:21–00:16:22 по Москве. Из них 9986 — метрики БД, 14 — успешные `/health`.
Событий обработки вопросов, вызовов ИИ и доставки в этом фрагменте нет.

| Операция | Число записей | Медиана, мс | p95, мс | Максимум, мс |
| --- | ---: | ---: | ---: | ---: |
| Запрос БД | 3334 | 2,08 | 3,77 | 17,20 |
| Получение соединения | 3332 | 2,51 | 4,27 | 17,93 |
| Транзакция | 3320 | 3,85 | 6,46 | 19,06 |

Записанные операции не показывают задержек БД в минуты. Это не исключает проблемы
в другом временном интервале и не устанавливает длительность вызова Timeweb.
Почти 24 строки в секунду фоновых метрик заполняют выгрузку в 10 000 строк примерно
за семь минут. Не установлено, что этот объём логирования вызвал задержку ответа.

Быстрые DB-метрики перенесены в `DEBUG`; операции от 100 мс остаются в `INFO`.
Все времена продолжают измеряться, события обработки запросов и ошибки сохраняются
в прежних уровнях. При необходимости детального разбора можно временно включить
`LOG_LEVEL=DEBUG`. После выпуска правки нужно зафиксировать время медленного вопроса,
режим Quick/Deep и выгрузить соответствующий интервал сразу после получения ответа.
