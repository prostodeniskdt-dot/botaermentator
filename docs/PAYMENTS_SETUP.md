# Подключение Tilda и Timeweb

Реализация подготовлена по ТЗ v3. Начисление по умолчанию отключено.
Реальный формат уведомления пока не подтверждён: см. [аудит](PAYMENTS_AUDIT.md).
Действия ниже выполняет владелец после разрешения на деплой; в рамках разработки
живой сайт, настройки Timeweb, ЮKassa и секреты не менялись.

## 1. Timeweb: подготовка и диагностический запуск

1. Сделайте резервную копию PostgreSQL. Сохраните текущие переменные окружения и версию образа.
2. В Cloud → App Platform → приложение Ферментатора откройте переменные окружения.
   Существующие настройки Telegram, базы и AI оставьте как есть.
3. Добавьте `PAYMENTS_ENABLED=false`, `PAYMENTS_CONTRACT={}`, `PAYMENTS_PACKAGES={}`.
4. Создайте случайный секрет, например локально `openssl rand -hex 32`.
   Запишите его только в `TILDA_WEBHOOK_SECRET` Timeweb и в закрытую настройку Tilda.
5. `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` берутся из того же магазина ЮKassa,
   который уже подключён к Tilda. Не создавайте новый магазин и не заменяйте его ключи.
   Для одного диагностического приёма эти две переменные ещё не требуются.
6. После отдельного разрешения опубликуйте новую версию приложения обычным Docker deployment.
   `scripts/start.sh` сам выполняет `alembic upgrade head` до запуска uvicorn.
   Проверьте в логах миграции `010_email_payments`, `011_admin_finite_balance`, `012_correct_owner_account` и успешный `/health`.
   Миграция 012 однократно устанавливает владельцу с подтверждённым ID 1221087257 баланс 100,
   отключает его безлимит и назначает email. Проверьте `/admin_user 1221087257`
   и `/admin_email 1221087257`; баланс после последующих запросов может уменьшаться.
7. Возьмите публичный HTTPS-домен **backend из Timeweb**, не домен Tilda.
   Точный путь приёмника: `https://<домен-backend>/payments/tilda/webhook`.
   Домен конкретного приложения в предоставленных данных отсутствует.
   Telegram продолжает использовать `/telegram/webhook`.

## 2. Регистрация получателя в боте

1. Пользователь запускает `/start`. Администратор при необходимости применяет обычный `/admin_allow <ID>`.
2. В личном чате с ботом администратор из `ADMIN_USER_IDS` выполняет
   `/admin_set_email <Telegram_ID> <email>`.
3. Проверяет `/admin_email <Telegram_ID>`; выводится маска.
4. Сообщает пользователю вводить в ST100 именно этот адрес. Регистр и крайние пробелы
   не влияют на поиск. Точки и `+suffix` сохраняются. Unicode local-part не поддержан;
   домены IDN переводятся в IDNA. Сам адрес не является Telegram-аутентификацией:
   покупка на чужой зарегистрированный email пополняет баланс владельца этого email.

## 3. Tilda: отдельный приёмник

1. Настройки сайта → Формы → Webhook: создайте **отдельный** приёмник с адресом из шага 1.7.
2. API NAME: `X-Tilda-Webhook-Key`; API KEY: тот же секрет, что в Timeweb.
   API Method: передача **в HTTP-заголовках**, не POST-поле.
3. Включите передачу товаров массивом и externalid, если доступно.
   Не включайте передачу cookies. Сверьте коды всех трёх товаров в каталоге.
4. Сохранение приёмника отправляет `test=test`: ожидается HTTP 200 без начисления.
   Если проверка не прошла, проверьте HTTPS, адрес backend, метод и секрет заголовка.
   Не ослабляйте проверку секрета для тестового запроса.
5. Редактор ST100 → Контент → Подключённые сервисы: отметьте новый Webhook,
   сохраните и опубликуйте страницу. Существующие приёмники сохраняются.
6. Настройки сайта → Платёжные системы → ЮKassa → включите
   «Отправлять данные в сервисы приема данных только после оплаты».
7. Сохраните и опубликуйте. Обязательное поле Email, дизайн, кнопка и переход на оплату сохраняются.
   **URL уведомлений ЮKassa для Tilda не заменяйте адресом бота.**

## 4. Обязательный живой аудит

1. Оставьте `PAYMENTS_ENABLED=false`. Зарегистрируйте тестового пользователя и email.
2. Владелец оформляет один реальный заказ через существующий сайт. Режим тестового магазина
   не используется для начисления: `test=true` сервер отвергает. Небольшая реальная
   тестовая цена допустима только после отдельного согласования; код цен не меняет.
3. Получите UUID из уведомления администратора; `/admin_payment_status <UUID>` покажет статус.
   В закрытой консоли БД посмотрите только структуру:
   `SELECT id, status, error_code, details->'shape' FROM purchase_orders ORDER BY created_at DESC LIMIT 5;`
4. Приватно получите обезличенный POST и ответ GET ЮKassa, как описано в аудите.
   Установите точные имена ключей; убедитесь, что provider payment ID действительно
   идентифицирует этот платёж и что ответ API содержит проверяемый ID этого заказа.
5. Сверьте каждый UID/externalid, количество, сумму в копейках и пакет кредитов с каталогом.
   Тестовые 1/2/3 ₽ из ТЗ не являются согласованным production-прайсом.
6. Если идентификатора платежа или связи с заказом нет — оставьте начисления отключёнными.

## 5. Контракт полей и включение

После аудита заполните `PAYMENTS_CONTRACT` JSON-объектом с ключами:
`audit_reference`, `email`, `lead_id`, `order_id`, `payment_id`, `products`, `sku`,
`quantity`, `amount`, `currency`, `provider_order_id`.
Значения путей берутся **только из образца**. Точное имя ключа, в том числе
`payment[systranid]`, поддерживается; вложенные JSON-пути разделяются точками.
`sku` и `quantity` отсчитываются от объекта строки товара; `provider_order_id` — от
объекта ответа ЮKassa. Никакого заранее предполагаемого `metadata.order_id` в production нет.
`audit_reference` — ссылка/номер закрытого отчёта с проверенными образцами.
Поддерживается ровно одна товарная строка, количество 1, RUB; остальные корзины идут на разбор.

`PAYMENTS_PACKAGES` — JSON вида
`{"<проверенный UID или SKU>":{"credits":50,"amount_kopecks":<согласованная цена в копейках>,"audit_reference":"<отчёт>"}}`.
Угловые скобки и пример цены необходимо заменить; это не готовый JSON для вставки.
Добавьте все три пакета после проверки. При приёме заказа сохраняется снимок цены и пути
связи с провайдером; последующее изменение прайса не переоценивает уже принятый заказ.

После отдельного разрешения на активацию, наличия отчёта и успешных проверок:

1. Заполните секреты магазина, контракт и пакетный справочник в Timeweb.
2. Включите `PAYMENTS_ENABLED=true`, примените окружение штатным перезапуском.
3. Выполните один новый оплаченный заказ. Проверьте `credited`, одну ledger-транзакцию,
   один outbox пользователя и `/balance`. Начальный баланс 5 + пакет 50 должен дать 55.
4. Повторите тот же POST несколько раз: баланс и доставленное уведомление не повторяются.
5. Проверьте неправильный email, сумму, чужой order ID и статус pending: грантов быть не должно.
6. Старые диагностические записи нельзя автоматически превратить в покупки:
   они не содержат исходного POST. После настройки контракта нужна контролируемая
   повторная доставка исходного заказа от доверенного источника и сверка на дубли.

## 6. Отключение

Установите `PAYMENTS_ENABLED=false` в Timeweb и примените окружение. Новых грантов не будет;
сохранённые уведомления могут доставляться. При необходимости снимите только новый
приёмник в ST100. Продажи Tilda/ЮKassa продолжат работать, потребуется ручная сверка.
Не откатывайте миграцию с удалением таблиц оплаченных заказов; сначала архивируйте данные.


Для дальнейшего аудита без SQL используйте раздел «Проверка ЮKassa из Telegram без
начисления» в [PAYMENTS_OPERATIONS.md](PAYMENTS_OPERATIONS.md). Старое уведомление,
сохранившее только структуру, нельзя проверить по API без новой доверенной доставки
идентификаторов. В новом диагностическом режиме сохраняется audit_input без email.

## Подтверждённый тестовый профиль 17.11.2026

После живого аудита `d061c9f3-4492-4664-ad89-05cc5b2b56e5` владелец подтвердил:

| externalid | Кредиты | Согласованная тестовая цена |
|---|---:|---:|
| PbhJaRz1P31ctv9EIgXm | 10 | 1 ₽ |
| EnvzUoDtB8uyPYfXBt5p | 50 | 2 ₽ |
| XCEUGyv0icslp5eph439 | 100 | 3 ₽ |

Для выбора этих кодов, цен и проверенной схемы достаточно одной переменной Timeweb:

```dotenv
PAYMENTS_PROFILE=tilda_test_2026_11_17
PAYMENTS_ENABLED=false
```

`PAYMENTS_CONTRACT` и `PAYMENTS_PACKAGES` удалите из окружения либо оставьте оба `{}`.
Профиль сам заполнит их внутри приложения; конфликтующие непустые custom-настройки
вызовут явную ошибку конфигурации, а не тихую подмену. ShopID/API secret сохраняются
в `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`. Webhook secret не меняется.

После применения окружения проверьте уже оплаченный заказ:

```text
/admin_payment_audit d061c9f3-4492-4664-ad89-05cc5b2b56e5
```

Ожидаются `configured_order_path_matches=true`, `configured_package_valid=true` и
`verified_credits=10` для этой покупки; остальные подтверждения оплаты и суммы сохраняются. Для этой проверки повторно платить не требуется.
Профиль не включает начисление сам: `PAYMENTS_ENABLED` остаётся отдельным выключателем.
Включать его следует только после успешного применения новой версии и проверки отчёта.
При `PAYMENTS_ENABLED=true` новые доверенные Webhook обрабатываются автоматически.
Ранее сохранённые диагностические записи не переезжают в очередь и не начисляются сами:
они не содержат исходный checkout-email; для них нужна отдельная безопасная сверка.

Профиль принимает одну строку товара, количество 1; сверяет цену строки, сумму строки,
итог и сумму ЮKassa с утверждённым справочником. Скидки и иные цены идут на разбор.
Отсутствующий Lead ID не заменяется Order ID: он остаётся NULL. RUB при отсутствии
валюты в Tilda задаётся явной серверной политикой профиля и независимо проверяется
в API ЮKassa; присланная отличная валюта не игнорируется. Связь заказа проверяется
строго через `metadata.tilda_orderid`, а не по description/email/сумме/времени.
Для боевых цен требуется новый согласованный прайс/профиль; тестовые цены не считаются
производственными по умолчанию.
