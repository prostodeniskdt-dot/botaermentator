# Эксплуатация начислений

## Email

Только личный чат и `ADMIN_USER_IDS`:

- `/admin_set_email <ID> <email>` назначает адрес существующему пользователю.
- `/admin_email <ID>` показывает маску.
- `/admin_clear_email <ID> CONFIRM` удаляет текущую привязку.

Адрес навсегда резервируется за первым Telegram ID, включая удалённый/заменённый.
Это исключает переезд задержавшихся заказов к новому владельцу email.
Повторно назначить адрес исходному владельцу можно; передать другому аккаунту нельзя.
Регистрация не одобряет доступ, не разблокирует и не выдаёт стартовые кредиты.

## Заказы и повторная проверка

Администратор получает UUID и причину `manual_review` без email.
`/admin_payment_status <UUID>` показывает статус и код.
`/admin_payment_retry <UUID>` повторяет проверку ЮKassa для сохранённого получателя,
не меняя payment ID, входные данные и снимок цены. Для начисленных заказов — без действия.
Время последнего retry хранится в `details.last_retry_at`.

Если email не был зарегистрирован при приёме, после ручной сверки исходного оплаченного
заказа и регистрации адреса используйте
`/admin_payment_resolve <UUID> <Telegram_ID> CONFIRM`.
Это явное назначение **только ранее не определённого** получателя; фиксируются администратор
и время. Текущий email должен совпадать с адресом заказа. Проверка оплаты всё равно обязательна.
Уже зафиксированный получатель никогда не заменяется. При смене его email заказ идёт на разбор;
восстановить старую привязку можно только исходному владельцу.
Диагностические записи без разобранных payment ID и email повторно не обрабатываются.
Конфликтующие POST с одним payment ID блокируют дальнейший retry до отдельного расследования.

## Очереди

HTTP подтверждает только запись в БД; API ЮKassa вызывается фоновым worker.
DB lock и unique payment ID защищают параллельные процессы. Ledger grant, статус credited
и запись уведомления коммитятся атомарно. UUIDv5 `yookassa:<payment_id>` обеспечивает
дополнительную идемпотентность существующего ledger. Два платежа одного email независимы.
Таймаут, HTTP 429/5xx, pending и waiting_for_capture повторяются с backoff до 1 часа.
Permanent API-ошибки, неизвестный SKU, неподтверждённая сумма/магазин/заказ идут на разбор.

Уведомление отправляется после commit. Временная ошибка повторяется отдельно от гранта;
после 10 ошибок статус failed, TelegramForbidden — blocked. Успешная доставка — sent.
Не сбрасывайте sent на pending без причины. Telegram не поддерживает идемпотентные sendMessage:
при падении процесса после фактической отправки, но до commit sent, возможен повтор сообщения.
Строгое exactly-once гарантируется для начисления; для такой неопределённости Telegram — нет.

## Возвраты и сверка

До гранта ненулевой refunded_amount блокирует выдачу. После гранта worker раз в сутки
повторно читает API ЮKassa для каждого credited-заказа. Полный/частичный возврат фиксирует
refunded и уведомляет администраторов. Кредиты автоматически не списываются; повторного
гранта не будет, поскольку credited_at сохраняется. Коррекцию решает администратор с журналом.
При сетевом сбое этой сверки повтор через час. Если магазин не передаёт refunded_amount,
автоматическое обнаружение невозможно — сверяйте возвраты в кабинете ЮKassa вручную.

Ежедневно сверяйте список оплат/возвратов в Tilda и ЮKassa с purchase_orders:
Tilda повторяет доставку ограниченно, полностью отсутствующий webhook backend обнаружить не может.
Проверьте pending_verification старше часа, manual_review, failed/blocked notices.

Безопасная сводка в закрытой консоли PostgreSQL:

```sql
SELECT id, status, error_code, recipient_id, provider_checked_at, credited_at
FROM purchase_orders ORDER BY created_at DESC LIMIT 100;
SELECT status, count(*) FROM payment_notices GROUP BY status;
```

Не публикуйте `details`, email, исходные POST, API-ответы и параметры SQL с PII.
Не включайте SQL echo и логирование HTTP-заголовков/тел запросов в production.
Отдельных событий с email или provider payload код платежей не пишет.

## Проверки разработки

Unit-тесты используют синтетический контракт, не реальные поля Tilda и не живую ЮKassa.
PostgreSQL-тесты используют `TEST_DATABASE_URL` только отдельной disposable БД с CREATEDB:
они создают и удаляют свои схемы и migration database. Никогда не задавайте production URL.

```sh
ruff check .
ruff format --check .
TEST_DATABASE_URL=<isolated-postgresql+asyncpg-url> pytest -q
```

Живой запуск остаётся заблокирован до завершения аудита в PAYMENTS_AUDIT.md.


## Структура Webhook прямо в Telegram

После обновления приложения в личном чате администратор может выполнить:

```text
/admin_payment_schema 9cb4432e-9e8a-404f-b8a7-a86453344ff3
```

Команда читает только указанный заказ и показывает сохранённую обезличенную структуру
уведомления: известные имена полей и типы значений. Email, ID платежа, значения полей,
секреты и произвольные имена полей не раскрываются. Неизвестные имена обозначены
`key_<хеш>`; восстановить исходные имена по этому выводу нельзя.
Для больших структур ответ делится на сообщения, после 24 000 символов обрезается
с явной отметкой. Для нормализованного заказа без исходной структуры это явно указано.
Неверный UUID даёт подсказку, отсутствующий заказ — сообщение «Заказ не найден».
Доступ разрешён только `ADMIN_USER_IDS` в личном чате.

Пришлите ответ команды для аудита полей. Это не подтверждение оплаты и не команда
начисления: баланс, заказ, конфигурация и платёжная очередь не меняются.
Если структура не содержит необходимых идентификаторов либо товарный массив пришёл
строкой, могут потребоваться дополнительные обезличенные данные из источника.
Повторную оплату только ради вызова команды делать не нужно.


## Проверка ЮKassa из Telegram без начисления

После обновления приложения:

1. В Timeweb оставьте `PAYMENTS_ENABLED=false`, `PAYMENTS_CONTRACT={}`,
   `PAYMENTS_PACKAGES={}`. Добавьте `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`
   того же магазина, который подключён к Tilda; это значения серверных API credentials,
   а не ключ Webhook. Секреты не присылайте в чат. Примените окружение приложения.
2. Сначала попробуйте повторную отправку уже оплаченного заказа в Tilda, если интерфейс
   действительно предоставляет эту возможность. Не предполагается существование такой
   кнопки во всех аккаунтах. Изменение настроек приёмника не пересылает заказ само по себе.
3. Если повтор недоступен, нужен отдельно согласованный новый контрольный заказ,
   выполненный владельцем через обычную корзину. Не оплачивайте много раз из-за отсутствия
   кредитов: в этом режиме отсутствие начисления ожидаемо.
4. Получите UUID из сообщения бота. При идентичном повторе старый UUID сохраняется,
   диагностические значения дополняются без смены получателя/статуса и без гранта.
5. В личном чате администратора выполните `/admin_payment_audit <UUID>` и пришлите
   весь ответ. Для просмотра структуры остаётся `/admin_payment_schema <UUID>`.

Команда проверяет API даже при `PAYMENTS_ENABLED=false`, но не создаёт и не подтверждает
платежи, не начисляет, не меняет статус заказа, получателя и очередь. В `details.audit_result`
записывается только отчёт, а в `audit_checked_by` — администратор; HTTP-ответ целиком не хранится.
Сетевой запрос выполняется вне транзакции БД, с таймаутом и без переходов по redirect.
Идентификаторы из диагностического audit_input не переносятся автоматически в боевые поля
purchase_orders: требуется отдельное подтверждение схемы и безопасная обработка заказа.

Основные ответы:

- `yookassa_credentials_missing`: нет ShopID/секретного ключа API магазина в окружении.
- `payment_id_not_captured`: старое уведомление содержало только структуру или ID не прошёл
  проверку формата; требуется свежая доверенная доставка заказа.
- `yookassa_http_401/403`: проверьте пару ShopID и API secret и доступ к этому магазину.
- `yookassa_http_404`: полученный systranid не найден в этом магазине; не подбирайте платёж
  по сумме/email/времени.
- `provider_temporarily_unavailable`: временная ошибка, повторите команду позже без новой оплаты.
- `provider_id_and_shop_match=false`: платёж не подтверждён как принадлежащий магазину.
- `exact_order_metadata_matches=[]`: стандартные поля metadata не установили связь с заказом.
  `order_token_in_description=true` сам по себе не разрешает начисление.

В Telegram выводятся признаки совпадения, денежные суммы/количество и структура ответа,
но не сам ID платежа/заказа, email, receipt, текст description и значения metadata.
Даже полностью успешный диагностический отчёт не включает начисления.

## Регистрация email новых пользователей

После миграции 013 новые записи пользователей требуют email и подтверждение ввода.
Техник получает адрес только после подтверждения. Ручная последовательность остаётся:
`/admin_set_email <ID> <email>`, затем `/admin_allow <ID>`. Для новой заявки без совпадающей
подтверждённой и зарегистрированной почты одобрение блокируется до изменения доступа
и гранта стартовых кредитов. Самостоятельного изменения платёжной привязки нет.
Предыдущие пользователи миграцией не переводятся на новую процедуру.
Подтверждение в Telegram не является проверкой владения email через письмо.
Заявки с email не выводятся списком и не логируются; полный адрес направляется
только самому пользователю и авторизованным администраторам для ручной регистрации.

Проверка обновления регистрации: полный pytest на отдельном PostgreSQL 16 — 540 passed,
без пропусков; одно предупреждение зависимости Starlette. Ruff и форматирование прошли.
Миграция проверена на существующих пользователях/балансах/истории: новая процедура для
них не включается. Проверены ручная регистрация, идемпотентность стартового гранта,
подтверждение/исправление адреса и запрет самостоятельной смены платёжной привязки.
