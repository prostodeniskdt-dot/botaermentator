# Fermentator Editorial — отчёт и проверка перед включением

## Статус

Реализация из PR №7 объединена в `main`. Все пять прежних веток GitHub удалены после проверки,
что их коммиты входят в `main`; дальнейшая работа ведётся непосредственно в `main` (см. AGENTS.md).
Настройки Timeweb не менялись, отдельная команда деплоя не выполнялась.
Начиная с версии `fermentator-editorial-2`, по умолчанию используются `ANSWER_RENDERER=editorial` и
`RICH_MESSAGES_ENABLED=false`: безопасное HTML-оформление включено, Rich активируется отдельно.
Реальная доставка и Telegram Desktop/Android/iOS в этой среде не
проверены: нет тестового токена и клиентов. Офлайн-превью не является скриншотом Telegram.

## Исправление таблиц и разрывов в версии 2

Ранее установка кода сама по себе не переключала `legacy`, поэтому длинные GFM-таблицы могли
показываться как текст с `|---|`, даже после обновления приложения. Теперь корректные таблицы
проходят общий структурный parser независимо от выбора legacy/editorial. При включённом Rich
это нативная таблица; без Rich — аккуратные карточки по строкам. В обычном Telegram HTML настоящие
таблицы не поддерживаются, поэтому HTML-резерв не выдаётся за сетку с ячейками.

HTML-план разделяет таблицу по целым строкам, а длинный список — по целым обычным пунктам.
Только одна строка/пункт, сама превышающая размер сообщения, требует внутреннего разделения.
В больших документах знакомые изолированные подписи («Варианты рецептов», «Технология
приготовления», «Контроль и диагностика», «Хранение» и другие из явного списка) получают уровень
заголовка без изменения текста. Короткие ответы этим правилом не превращаются в статьи.

Старые явно заданные переменные окружения всё ещё имеют приоритет над defaults. Для нативных
таблиц используются `ANSWER_RENDERER=editorial` и `RICH_MESSAGES_ENABLED=true`; выбранный legacy
тоже имеет совместимый путь таблиц, но не включает Rich при его выключенном флаге. Сохранённые
планы версии 1 завершаются по своим payload без пересборки и повторной отправки.

Администратор может выполнить `/admin_format` в личном чате. Команда показывает версию renderer,
фактические флаги, версию aiogram и три последние собственные доставки: версию плана, запрошенный
формат, подтверждённо отправленные части и машинную причину HTML fallback. Полные вопросы,
ответы и секреты не выводятся. Если команда не распознаётся, приложение ещё не использует этот
код либо у пользователя нет административного доступа. Флаги также записываются безопасными
полями в событии `app_starting`.

## Аудит

- Старый Rich-путь ограничивался коротким Markdown, помещающимся в одну HTML-часть.
- CommonMark без таблиц терял структуру GFM; заголовки и цитаты становились обычным текстом.
- Наличие любого HTML переключало весь ответ на sanitizer, поэтому смешанный Markdown мог
  показываться буквально. Новая система разбирает обе структуры совместно.
- Любой `TelegramBadRequest` раньше мог запускать HTML fallback, включая ошибки чата и темы.
  Теперь смена представления разрешается только при явном отказе по разметке, размеру или методу.
- Существующие очередь, lease, привязка всех message ID к BotResponse и списание кредитов пригодны
  для нового форматирования. Их бизнес-логика сохранена; резервные части требуют отдельного
  сохранённого состояния и фильтрации при установке кнопки расширения.
- Обнаружена дополнительная потеря данных в стандартном GFM: лишние ячейки относительно шапки
  отбрасываются парсером. Новый адаптер сохраняет их и дополняет отсутствующие заголовки пустыми.
  Явные номера этапов, включая последовательность `3, 8, 10`, также сохраняются.

Проверено с aiogram **3.31.0**, markdown-it-py **4.2.0**, mdit-py-plugins **0.6.1**.
Минимальная версия aiogram поднята до 3.31; дублирующая зависимость Markdown удалена.

## Архитектура

`Исходный ответ → ResponseParser → Document → editorial_rules → semantic_split → PlannedPart → очередь`

| Компонент | Назначение |
| --- | --- |
| `app/bot/formatting/editorial/document.py` | Неизменяемые блоки, inline-узлы, ячейки и исходный source |
| `parser.py` | Markdown-it, GFM-таблицы, ссылки/сноски, LaTeX, HTMLParser для смешанного HTML |
| `rules.py` | Только осторожное оформление известных подписей параметров |
| `renderers.py` | Typed Rich Blocks и обычный безопасный HTML из одной модели |
| `splitter.py` | Проверка лимитов, специализированное разбиение и выбор смысловых границ |
| `app/bot/formatting/plan.py` | Единый переключатель, версия плана, HTML-резерв и классификация отказов |
| `app/services/delivery_service.py` | Отправка сохранённого плана и подтверждённый прогресс |

Редакционный renderer использует Typed Blocks для всего сообщения. Это позволяет точно считать
структуру и не передавать повторно Markdown на серверный разбор. Старый Rich Markdown доступен
через legacy. Входной HTML преобразуется в ту же модель; одно InputRichMessage содержит только
`blocks`, без одновременного `html`/`markdown`.

Заголовки сохраняют уровни 1–6; списки — порядок, вложенность и явные номера. Корректные GFM-таблицы
становятся нативными таблицами с шапкой, выравниванием и compact-режимом. Цитаты становятся
blockquote, сноски сохраняют метки и публичные ссылки. Details открыты по умолчанию. Входной
expandable blockquote оставляется обычной видимой цитатой: у этого типа нет подтверждённого
параметра начального раскрытия, а renderer не должен решать, безопасно ли скрывать произвольный текст.

Новые заголовки, таблицы, выводы, источники и советы не придумываются. Умеренное автоматическое
выделение применяется только к подписи в начале абзаца, например «Температура:», а не ко всем числам.
Не менялись инструкции агентов, модели, Quick/Deep, продолжения, память, кэширование исходных
ответов, кредитные цены, рекомендации или требования пищевой безопасности. Дополнительных AI-вызовов нет.

## Лимиты и разбиение

Сверка с [Telegram Bot API](https://core.telegram.org/bots/api#rich-message-formatting-options):
публичные пределы составляют 32768 символов текста, 500 блоков с вложенными элементами,
16 уровней и 20 столбцов. Используется запас: 30000 символов, 450 блоков, 14 уровней и 20 столбцов.
Дополнительно ограничена оценка JSON полезной нагрузки 512000 байт с обычной JSON-сериализацией
SDK. Это собственный защитный предел, а не заявленный Telegram лимит байтов. Формулы входят в
длину текста; строки таблиц и пункты списков входят в число блоков.

Если документ проходит ограничения, он отправляется одной Rich-частью. В остальных случаях
разделяются целые блоки. Алгоритм сначала минимизирует число сообщений для подготовленных
неделимых единиц, затем предпочитает границы крупных разделов, подразделов и абзацев. Заголовок
сохраняется с первым следующим блоком, когда это возможно при выбранном числе сообщений.

Большая таблица делится по строкам с повтором шапки. Слишком широкая таблица или отдельная
непомещающаяся строка превращается в понятные строки параметров без удаления значений. Короткие
списки и цитаты остаются целыми. Только чрезмерно большие абзацы/пункты/код требуют внутреннего
разделения: предложения/строки, затем пробелы, и лишь для одного огромного токена — символы.
Код сохраняет пробелы; слишком большая формула показывается как LaTeX source, а не как неверные
кусочки формулы. Чрезмерная вложенность упрощается с сохранением текста, ссылок и номеров.

## Доставка и миграция 009

Миграция `009_editorial_delivery` добавляет только JSONB `telegram_delivery_parts.payload`, по
умолчанию `{}`. Существующие тексты, состояния и message ID не меняются. Старые HTML/Rich-задания
остаются читаемыми; миграционный тест проверяет старую подтверждённую часть.

План целиком сохраняется до сетевой отправки одним пакетным INSERT. Rich-часть хранит версию,
типизированный primary и индексы заранее подготовленных HTML-частей. Эти части имеют состояние
`standby`. Успех Rich оставляет их неактивными. Подтверждённый отказ по размеру/разметке атомарно
переводит родителя в `fallback`, а резервные части — в `pending`. Каждый HTML message ID после
отправки сохраняется отдельно в той же существующей таблице.

Повтор использует сохранённый payload и HTML, даже если renderer уже переключили на legacy.
Подтверждённые `sent` пропускаются; `sending`/`unknown` не переотправляются автоматически. Ошибки
чата/темы/доступа и сетевые таймауты не запускают альтернативную отправку. Изменение версии
renderer не меняет уже подготовленный план. Старые задания без частей на повторной попытке
сохраняют прежнюю защиту от неизвестного результата.

Кнопка «Раскрыть подробнее» ставится на последнюю реально отправленную часть, исключая standby.
Её цена и callback не менялись. Любой отправленный резервный message ID участвует в существующем
поиске исходного BotResponse. Темы групп, reply routing и нижнее меню сохранены.

Прямая отправка использует тот же build_plan и classifier, но режим `STORE_BOT_RESPONSES=false`
по-прежнему не обладает долговременным прогрессом очереди. Для восстановления после перезапуска
нужен обычный production-режим с PostgreSQL и сохранением ответов.

## Проверки и примеры

Эталонные синтетические Markdown-файлы: `tests/fixtures/editorial/quick.md`, `deep.md`, `research.md`,
`mixed.md`, `recipe_comparison.md`. Они не содержат закрытой базы знаний или пользовательских диалогов.

```bash
python -m scripts.editorial_review --runs 10
```

Результаты в `review/editorial/` (не коммитятся):

- `before-after.html` — одинаковые исходники через legacy и модель Editorial;
- `plans.json` — фактические Rich-payload и HTML-резервы;
- `benchmark.json` — воспроизводимые CPU-замеры.

Например, входная GFM-таблица «Показатель / Значение» раньше теряла табличную структуру. Теперь это
`type=table` с нативными ячейками, а резерв — строки «Температура — 22 °C». Одинаковая статья на
6630 символов раньше давала 2 HTML-сообщения, теперь — 1 Rich с 3 заранее подготовленными HTML
частями на случай отказа. Офлайн HTML показывает структуру, а не внешний вид Telegram-клиента.

Локальные медианы первоначальной версии (10 запусков) сохранены в `EDITORIAL_BENCHMARK.json`:

| Пример | Символов | Legacy, мс | Editorial, мс | Сообщений до → после |
| --- | ---: | ---: | ---: | ---: |
| Quick | 213 | 0,44 | 0,78 | 1 → 1 |
| Deep | 814 | 1,23 | 1,84 | 1 → 1 |
| Исследование | 536 | 0,19 | 1,54 | 1 → 1 |
| Статья | 6630 | 7,66 | 10,05 | 2 → 1 |
| 600 строк таблицы | 15411 | 12,27 | 62,82 | 5 → 2 |

Это время разбора, preflight и подготовки HTML-резерва. Оно не измеряет Timeweb, Telegram или
пользовательскую задержку. Большая таблица проверяется по накопительным размерам, без повторного
рендеринга всех растущих строк. JSON-план повторно не рендерится при восстановлении.

Метрики: `editorial_plan_ready` (parse_ms, prepare_ms, блоки, число сообщений, формат, причина
fallback), `editorial_delivery_fallback` (категория подтверждённого отказа),
`editorial_delivery_finished` (фактическое число сообщений и время этой попытки). Сохраняются
существующие timings отдельных отправок. Счётчик ошибок разметки не содержит тело Telegram error.
Полные вопросы, ответы, авторские материалы и секреты в эти события не записываются.

Проверки охватывают native SDK schema, числа/единицы/предупреждения, незакрытый Markdown/HTML,
Unicode, длинные блоки, таблицы/ссылки/формулы/сноски, повтор и сетевую неопределённость,
Rich→несколько HTML, откат renderer между попытками, цену расширения, бесплатный cache hit,
кнопку последней части, темы групп и совместимость миграции. Полный набор также проверяет прежние
Quick/Deep, технические продолжения, кредиты и сохранность данных.

```bash
ruff check .
ruff format --check .
python scripts/sync_prompt_docs.py --check
TEST_DATABASE_URL=<isolated-postgresql-url> pytest
```

## Живая проверка и контролируемое включение

Сначала запуск без сети:

```bash
python -m scripts.editorial_smoke
```

Для проверки в собственном тестовом чате оператор задаёт
`TELEGRAM_BOT_TOKEN` через окружение и выполняет:

```bash
python -m scripts.editorial_smoke --send --chat-id <test-chat-id> --example deep --check-button
```

Для форума доступен `--topic-id`. Скрипт использует тот же прямой sender, добавляет тестовую подпись
и при необходимости пример кнопки, не вызывает AI/Timeweb/БД и не списывает кредиты. Без `--send`
ничего не отправляет. Реальная отправка в рамках этой разработки не выполнялась. Тестовая кнопка
не заменяет проверку платного расширения через штатный staging-бот; его сохранённые связи и цена
проверяются интеграционными тестами.

Обязательная ручная матрица перед включением: Desktop, Android, iOS при доступности. Проверить
плотность и иерархию, шапки/выравнивание таблиц, Unicode, формулы, открытые Details и цитаты,
ссылки, кнопку расширения, нижнее меню, темы и ответ на последнюю часть. Сохранить настоящие
скриншоты и фактические результаты. Здесь эта матрица остаётся невыполненной.

После ревью и этих проверок — согласованный deploy с миграцией 009 и флагами:

```env
ANSWER_RENDERER=editorial
RICH_MESSAGES_ENABLED=true
```

Не запускать старые и новые consumers одновременно: старый код не знает standby/fallback.
Быстрый откат — `ANSWER_RENDERER=legacy` при сохранении нового кода и схемы. Для возврата
к обычному HTML также `RICH_MESSAGES_ENABLED=false`. Это не меняет кредиты или исходные ответы,
а уже сохранённые задания завершаются по своей версии. Откат бинарного кода/удаление payload при
незавершённых новых заданиях не является безопасным быстрым откатом.

Известные границы: HTML разбирается как содержимое, а не как браузер с CSS; произвольные стили и
сложные объединения ячеек требуют отдельных эталонов. Нестандартный Markdown, недоступный
поддержанным расширениям, сохраняется читаемым текстом. Поддержка новых Rich возможностей на
конкретном сервере/устройстве подтверждается только живой проверкой. Ни скриншоты, ни успех
реальной доставки не заявляются на основании mock-тестов.
