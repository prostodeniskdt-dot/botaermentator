# Диагностика и проверка доработки

Исходная версия: `main`, `18777f204fd9156fb252ba677ac8e827ea24f558`. Основание — утверждённый пользователем план по ТЗ публичных тестов 05.10 и 14.10.2026. Production и реальные пользовательские данные не использовались.

## Подтверждённые дефекты исходной версии

1. `update_queue.py` последовательно ожидал `feed_update` и доставку. Синтетические два задания по 80 мс задерживали третье до 165 мс. Это демонстрация устройства очереди, не измерение production.
2. Question routers удерживали DB-транзакцию на протяжении внешних ИИ-вызовов. Ранний commit без замены `pg_try_advisory_xact_lock` ослабил бы защиту пользователя.
3. История третьего агента уже была ограничена, но второй агент получал предыдущий ответ целиком. Причина всех production-задержек этим не установлена.
4. Обычные стикеры без текста уже игнорировались. При этом emoji-only и невидимые символы проходили gate, а анимация с подписью могла попасть в групповой запрос. Упоминание после символа вне BMP обрабатывалось с неверными offsets.
5. HTML splitter разрывал теги. Ошибка второй Rich-части включала HTML-повтор всего ответа. Очередь доставки не хранила прогресс частей.
6. Клиент терял `choices[0].finish_reason`, не учитывал Responses incomplete_details и не ограничивал весь вызов общим deadline.
7. Баланс не вычитал резерв. FAQ-кэш не учитывал уровень и мог включать персонализированные ответы.

## Реализованные изменения

- Отдельные ограниченные потребители вопросов, служебных команд и доставки; PostgreSQL остаётся единственной очередью.
- Межпроцессная аренда пользователя с heartbeat и проверкой владельца; стабильный request_id и сохранённый вопрос до первого ИИ-вызова, включая классификацию контекста.
- Commit до внешних вызовов. Неоконченные запросы после потери аренды завершаются ошибкой с освобождением резерва; сохранённые ответы продолжают доставку без повторной генерации.
- Отправка через outbox также при прямой обработке webhook, если включено сохранение ответов. При выключенном сохранении ответов доставка остаётся прямой, без долговечного восстановления текста.
- Сохранение прогресса частей и привязка reply к любой части. Длинный Markdown преобразуется в ограниченный HTML и делится с балансировкой тегов/сущностей и учётом UTF-16. Короткие ответы сохраняют Rich Messages.
- Временные уведомления с очисткой после последней части, при ошибке и после восстановления приложения.
- Необязательный уровень в существующем profile_facts, независимый Quick/Deep, изолированные ключи кэша и исключение личных фактов из общего FAQ.
- Одно расширение на исходный ответ с отдельной ценой, снимком контекста и прежними исключениями credit service.
- Детерминированные рекомендации без дополнительного ИИ-вызова, общие для свежих и кэшированных ответов.

## Измерения

Structured events включают `stage_timing` для приёма/обработки update, полного вызова агента, каждой HTTP-попытки и отправки части; `update_queue_wait`, `db_checkout_timing`, `db_query_timing`, `db_transaction_timing`. Используются монотонные часы, а для долговечного ожидания — timestamps очереди. Сквозная связь — update_id/request_id и delivery_id.

SQL-параметры скрыты; тела ошибок провайдера, тексты вопросов и кэш-ключи с вопросами в новые метрики не попадают. AIUsageEvent сохраняется; latency вызова включает перебор транспортов и backoff.

Сравнивать p50/p95 отдельно для ожидания очереди, БД, агентов и доставки. В тестах баланс третьего пользователя доступен, пока два ИИ-вызова заблокированы; числового ускорения production это не доказывает.

## Миграции

- `006_processing_delivery`: аренды пользователя, уведомления, части доставки, техническая категория update.
- `007_answer_expansions`: снимок контекста BotResponse и уникальная операция расширения.

Тест миграции создаёт отдельную БД, применяет 005, заполняет профиль, диалог, ответы, баланс, ledger и очереди синтетическими данными, затем проверяет upgrade, downgrade до 005 и повторный upgrade. Старые столбцы и записи сравниваются полностью.

Старые завершённые доставки не повторяются. Старые pending без попыток получают план частей при первой доставке. Для старых in-flight доставок без прогресса автоматический повтор запрещён, поскольку факт предыдущей отправки неизвестен.

## Обязательные проверки

```bash
ruff check .
ruff format --check .
TEST_DATABASE_URL=postgresql+asyncpg://test_user@127.0.0.1:55432/test_db pytest
```

TEST_DATABASE_URL должен указывать на изолированную тестовую БД. Workflow-тесты создают уникальные схемы и удаляют их; тест миграции требует CREATEDB и создаёт/удаляет отдельную БД. При отсутствии TEST_DATABASE_URL PostgreSQL-тесты явно пропускаются — такой запуск сам по себе не подтверждает транзакционную устойчивость.

Проверки выполнены на Python 3.12 и изолированном PostgreSQL 16: `ruff check .` и `ruff format --check .` успешны; `pytest` с TEST_DATABASE_URL — **170 passed** (исходная версия: 96 passed). Осталось одно предупреждение об устаревшем API зависимости Starlette TestClient.

Автотесты покрывают очередь/баланс, доставку и удаление уведомлений, рестарт/резервы, lease fencing, уровни и кэш, двойные и одновременные expansion-клики, недостаток средств/ошибку генерации, admin/unlimited, очистку памяти во время генерации, рекомендации, безопасное форматирование и неизменность safety-блока промпта.

## Проверки, требующие стенда Timeweb/Telegram

В окружении не предоставлены Timeweb/Telegram credentials и доступ к настройкам KB. Поэтому фактическое подключение доверенных материалов, отсутствие скрытой памяти у провайдера, качество реальных ответов, лимиты модели и поддержка Rich API должны проверяться отдельно. Существующие output defaults 600/2200 сохранены; 1000/4000 — кандидаты для стенда, не подтверждённые production-значения. Лимиты передаются во всех вариантах API; усечение отмечается явно и не кэшируется как полный ответ.

Отправка Telegram и DB commit не атомарны. Подтверждённые части не повторяются; `sending/unknown` после неоднозначного сбоя требует разбора, а не слепого resend. Аналогичное окно существует между отправкой уведомления и сохранением его ID. Абсолютное exactly-once без поддержки провайдера не заявляется.

При выпуске нельзя одновременно запускать старый и новый worker на одной очереди. Сначала остановить старых потребителей и учесть in-flight, затем применить добавочные миграции и запустить новую версию. Параллелизм задаётся на процесс: число процессов учитывается при расчёте общей нагрузки на Timeweb и PostgreSQL. Автоматический деплой, изменение production-секретов и реальные платные вызовы в эту работу не входили и не выполнялись.
